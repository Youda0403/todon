# 기록에 나타난 타래 대기와 본문 우선 표시

비교 기준: main `2462e5ba6a9a1cf65be00402b95c06d2a0f2f2ec`.

## 확인된 구간

기기 기록에서 본문과 타래의 완료 시각 및 소요 시간을 역산하면 다음 요청들이
같거나 거의 같은 시각에 시작했다. 요청을 묶는 번호가 없던 기록이므로 쌍은 추정이다.

| 본문 조회 | 타래 조회 | 이전 코드의 전체 대기 |
| --- | --- | --- |
| 1,351ms | 9,396ms | 약 9.4초 |
| 523ms | 4,547ms | 약 4.5초 |
| 8,007ms | 8,713ms | 약 8.7초 |

이전 코드는 Promise.all이 끝나야 본문도 표시했다. 따라서 타래가 늦으면 먼저 도착한
본문을 읽을 수 없었다. 본문 자체가 8초 걸린 사례도 있어 타래 대기만으로 모두 설명되지는 않는다.
기록의 시간은 API 함수 전체 시간이다. 서버 처리, 통신, 브라우저 작업의 비중은 분리하지 못한다.
모든 요청이 GET이므로 이 기록으로 실제 글 전송 POST 지연을 판정할 수는 없다.

## 본문과 타래

- 목록에서 누른 툿의 이미 받은 본문을 즉시 사용하고, 서버의 최신 본문과 타래를 병렬 확인한다.
- 받은 본문은 계정·서버를 구분해 메모리에 최대 200개 보관하고 5분 이내의 항목만 재사용한다. 누른 카드는 그 시점에 다시
  보관하므로 오래 읽은 목록에서도 다른 조회로 메모리 항목이 밀려난 영향을 피한다.
- 보관된 본문이 없어도 본문 응답이 오면 타래보다 먼저 보여 준다.
- 타래가 완성되기 전에는 불러오는 중임을 표시하고 확정 답글 개수를 표시하지 않는다.
- 뒤늦게 이전 글과 답글이 붙어도 선택한 툿의 화면 위치를 보존한다.
- 네트워크·타래 오류는 읽을 수 있는 본문과 재시도 안내를 남긴다. 삭제·열람 불가 및
  인증·권한 오류가 확인되면 보관된 본문도 걷어낸다.
- 다른 화면으로 이동하면 해당 타래의 클라이언트 요청을 취소하고 늦은 결과를 무시한다.
  돌아오면 미완료 조회만 다시 시작한다. 완료된 뒤로가기 화면은 기존 캐시를 사용한다.
- 확인 중 작성한 답글은 이전에 시작한 응답이 도착해도 보존한다.

## 알림 정리 조회의 422

기존 구현이 한 번에 최대 80개를 보냈지만 Mastodon의 상태 묶음 조회 제한은 20개다.
공식 StatusesController의 check_statuses_limit와 Api::BaseController의
DEFAULT_STATUSES_LIMIT = 20을 확인했다. 기록의 422 응답 메시지는 없으므로 이 오류의
정확한 서버 측 이유는 확정하지 않는다. 제한을 넘는 요청은 코드에서 확인돼 수정했다.

최대 80개 확인 대상을 20개씩 나누어 뒤에서 확인한다. 거절된 요청으로 알림을 지우지 않는다.
20개 요청도 422·404·405·501로 거절하는 서버는 해당 세션의 묶음 확인을 중단한다.
개별 툿 열기 및 알림 목록 갱신에 따른 기존 정리는 유지한다.

## 추가 기록과 검증

진단 버전은 2026-10-18.5다. 숫자 순번과 타래별 묶음 번호, 요청 작업 종류,
헤더 수신까지·본문 읽기·JSON 처리 시간, 성공/취소/시간 초과를 추가한다.
타래의 첫 본문 DOM 준비와 전체 DOM 구성 시간도 기록한다. 실제 픽셀 표시 시간 측정은 아니다.
본문·주소·계정·토큰·보관된 본문은 진단 복사에 넣지 않는다.

`node --test tests/*.test.cjs`: 91개 통과.

별도 모바일 Chromium 14개 시나리오: 보관 본문 즉시 표시, 최신 본문 우선 도착,
타래 도착 시 읽던 위치, 직접 답글 개수, 진단 묶음 번호, 재시도, 삭제·권한 오류,
이탈 시 취소와 늦은 응답 무시, 실제 멘션 카드 클릭, 확인 중 답글 작성,
80개 알림의 20개 단위 조회를 검사했다. 삼성 브라우저 실기기의 개선률은 아직 측정하지 못했다.
