# 표시한 알림과 클릭 대상 툿의 연결

비교 기준: main `5f2f30fe36569aa4de24172908ef72ae7a78a693`.

## 이번 기록에서 확인한 범위

2026-10-19 23:18 KST, 진단 버전 2026-10-19.1.
`notification-open`부터 계정 확인, 알림 단건 조회, 타래 진입까지 연결되어 있다.
계정 확인과 알림 ID 비교가 통과했고, 다른 클릭·수동 이동·취소가 끼어든 기록은 없다.
알림 조회는 243ms, 타래 본문과 문맥 조회는 각각 110ms와 102ms에 성공했다.
따라서 이번 기록에서 이전 응답이 뒤늦게 화면을 덮었다고 판단할 근거는 없다.

`notification-resolved.matched: true`는 요청한 알림 ID와 응답 ID가 같다는 뜻이다.
휴대폰 알림에 표시됐던 툿과 클릭 후 툿이 같다는 검사는 없었다.
서비스 워커가 제목·본문을 만든 시점의 툿 대상을 Notification.data에 남기지 않고,
클릭 시 알림 ID만 다시 조회해 그때의 대상을 신뢰했다.
이 때문에 표시 시점과 클릭 시점의 차이를 검사하거나 당시 기록으로 구분할 수 없었다.
휴대폰에서 실제로 어떤 두 툿이 달랐는지는 이 기록만으로 확정하지 않는다.

## 변경

- 서비스 워커가 확인한 한 알림 응답에서 제목·본문과 이동 대상 종류·ID를 함께 만든다.
  시스템 알림에는 수신 계정 지문, 알림 ID와 함께 이 대상 및 프로토콜 버전을 담는다.
- 클릭 시 수신 계정과 알림 ID에 이어, 표시 당시 대상 종류와 ID가 조회 결과와
  모두 같아야 이동한다. 다르면 설명과 함께 수신 계정의 알림 목록을 연다.
- 상세 조회 실패로 원래 푸시의 간단한 문구만 표시한 알림은 목록 전용으로 만든다.
  나중에 다른 조회 결과로 툿 대상을 추측하지 않는다.
- 예전에 생성된 시스템 알림과 `#/open/...` 주소에는 확인된 대상이 없으므로
  수신 계정 확인 후 알림 목록으로 안내한다. 새 알림은 `#/notice/...` 주소를 쓴다.
  예전 화면 코드가 새 주소를 예전 직접 이동으로 해석하지 못하도록 경로를 구분했다.
  새 워커와 예전 화면 코드가 함께 실행되는 경우 예전 화면은 홈을 표시할 수 있다.
- 계정별로 같은 알림 ID가 있어도 시스템 알림 태그가 충돌하지 않도록 계정 지문을 포함한다.
- 부스트 래퍼가 있으면 표시 본문과 이동 모두 원본 툿을 기준으로 한다.
  툿이 필요한 알림에서 툿 정보가 없으면 프로필로 대신 이동하지 않는다.
- 앱 안 팝업도 표시 시점의 주소와 본문 스냅샷을 잡아 둔다.
  이후 원본 알림 객체가 바뀌어도 클릭 대상이 바뀌지 않는다.
- 기존 최신 클릭 검사, 이동 취소, 수신 계정 고정, 창 범위 제한과 전달 응답 처리는 유지한다.

## 진단과 업데이트

화면·워커 버전은 2026-10-19.2, 새 알림 이동 프로토콜은 2.
알림 ID 일치와 별도로 `targetMatched`를 기록하며, 알림 종류와 부모 툿 유무도 남긴다.
확인된 대상이 없는 경우 `legacy` 또는 `unverified-display`를 구별한다.
워커에 실제 실행 버전을 물어 `worker-info`로 남기고 등록 시 스크립트 HTTP 캐시를 우회한다.
본문·계정·토큰·지문·알림 번호·툿 번호·주소는 복사 기록에 추가하지 않는다.

  워커 탐색 대체 처리와 앱 라우터·DOM 렌더링을 실행했다.

  - 예전 화면과 새 워커가 함께 실행될 때 잘못된 직접 이동 방지
  - 두 계정의 동일 알림 ID, 부스트 원본 툿, 팝업 객체 변경
