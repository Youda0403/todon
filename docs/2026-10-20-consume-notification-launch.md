# 앱을 켰을 때 남아 있던 알림 경로가 실행되는 문제

비교 기준: main `1bb0bd8f0321dba3ff8d5d0fdf028da00a3a215b`.
화면·서비스 워커 버전: 2026-10-20.5. 알림 이동 프로토콜: 3.

## 사용자 기록과 재현

2026-10-20 18:38 KST, 진단 버전 2026-10-20.4, 워커 2026-10-19.2.
사용자는 알림을 누르지 않고 앱 아이콘으로 들어갔다고 보고했다.
첫 이벤트가 `notification-open`이며, 그 앞에 시스템 메시지를 받았다는
`notification-click`은 없다. 워커 버전 확인보다도 알림 열기가 먼저 시작됐다.
이어서 계정 확인과 좋아요(`favourite`) 알림의 단건 조회가 성공했고,
표시 대상과 조회 대상이 일치해(`targetMatched: true`) 답글인 툿으로 이동했다.

코드에서는 초기 URL이 `#/notice/...`이면 실제로 새 알림을 클릭했는지 확인하지 않고
바로 `openNotif`을 실행했다. 계정·알림 ID·툿 번호 검사는 있었지만 새 클릭과
복원된 예전 주소를 구분하지 못했다. 이전 HTML을 실제 모바일 Chromium에서
예전 알림 주소로 실행해, 새 클릭 이벤트 없이 단건 조회와 툿 이동이 발생함을 재현했다.
삼성 브라우저가 당시 주소를 저장·복원한 구체적인 시점까지 이 기록으로 확정하지는 않는다.

## 수정

- 실제 서비스 워커 `notificationclick`마다 무작위 128비트 번호를 발급하고,
  표시한 대상과 수신 계정에 연결된 알림 주소에 붙인다.
- 워커 메타데이터 캐시에 미처리 클릭 주소와 발급 시각만 저장한다.
  최대 20개·유효시간 2분으로 제한하며 발급·확인 때 만료 항목을 정리한다.
  토큰·툿 본문을 추가 저장하지 않는다.
- 앱은 계정을 선택하거나 알림 API를 조회하기 전에, 활성 워커에 MessageChannel로
  그 주소의 일회성 사용을 요청한다. 워커는 앱 범위의 창인지와 발급 주소를 확인하고
  동일 큐 안에서 사용 처리·삭제를 끝낸 뒤 응답한다.
  워커가 재시작되어도 캐시의 사용 처리 결과는 유지된다.
- 이미 사용했거나 발급하지 않았거나 만료된 주소, 시작 시 복원된 옛 `notice`·`open`
  주소는 단건 알림 조회와 계정 전환 없이 홈으로 간다. 홈의 history 깊이도 0으로 정리한다.
  확인 요청은 최대 2.5초로 제한하고 실패 시 무한 로딩하지 않는다.
- 실제 알림을 다시 클릭하면 같은 알림이어도 새 번호를 발급하므로 정상적으로 다시 열린다.
  앱이 이미 열린 경우의 전달, 응답이 없는 경우의 탐색 대체, 새 창 실행에 같은 확인을 적용한다.
- 이전 워커가 보낸 실제 실시간 전달은 한 번의 메모리 신호로 인식해 기존 동작을 지원한다.
  같은 옛 주소가 나중에 초기 URL로 복원된 경우에는 허용하지 않는다.
- 새 워커는 기존 프로토콜 2 알림도 그 알림에 저장된 대상을 유지해 새 클릭 번호를 붙인다.
  예전부터 대상이 확인되지 않은 알림은 계속 수신 계정의 알림 목록으로 안내한다.
- 계정 고정·알림 ID 일치·표시한 툿 일치·가장 최근 이동 우선 처리는 그대로 유지한다.
  일반 툿 링크와 읽던 화면으로 돌아가는 동작, 인용 카드 갱신 코드는 변경하지 않는다.

## 진단과 검증

`notification-open`에 URL·실시간 전달 구분과 프로토콜 버전을 추가하고,
`notification-launch`에 새 클릭 확인 성공 여부를 기록한다.
번호·주소·수신 계정 지문·토큰·본문·무작위 확인 번호를 복사 기록에 넣지 않는다.

- `node --test tests/*.test.cjs`: 216개 통과. 복원 주소, 중복 사용, 연속 클릭,
  늦은 확인 응답, 워커 재시작, 동시 확인, 만료, 범위·대상 변경, 저장 실패,
  이력 깊이·확인 실패에 대한 회귀 검사 16개를 추가했다.
- 전체 앱 스크립트 구문 검사, `node --check sw.js`, `git diff --check` 통과.
- HTTPS 로컬 서버·실제 Chromium 서비스 워커·411×922 모바일 화면·통제된 API로
  13개 항목을 확인했다. 기존 현상 재현, 앱 창이 없는 클릭, 사용한 주소 복원,
  프로토콜 2·옛 open 주소 복원, 발급하지 않은 주소, 일반 시작, 열린 앱의 클릭,
  동일 알림 재클릭, 전달 무응답 후 탐색, 대상 불일치 거부, 미처리 주소 만료,
  복사 진단 정보의 비밀 정보 미포함을 검사했다. 브라우저 스크립트 오류는 없었다.
  OS 알림 클릭은 테스트용 신호로 실제 클릭 핸들러를 호출하고,
  창 열기 API 인자를 수집한 뒤 실제 URL로 이동했다. 서비스 워커 캐시·메시지 전달·
  확인·창 탐색·앱 렌더링은 실제로 실행했다.
- 사용자의 서버에는 쓰기 요청을 보내지 않았다. 실제 삼성 기기의 앱 아이콘·OS 알림판
  동작을 직접 실행한 결과까지 확인한 것은 아니다.
