# 휴대폰 알림 연결 점검과 복구

2026-10-16 추가. 비교 기준: main의 91e5233.

## 확인된 사실과 원인 추정

푸시 알림이 오지 않다가 알림을 껐다 켠 뒤 다시 수신되는 현상이 있었다.
이 결과는 알림 연결 재등록으로 복구됐다는 근거다. 만료, 브라우저 변경,
푸시 서비스의 거절 중 무엇이 최초 계기였는지는 당시 서버·휴대폰 기록이 없어 확정할 수 없다.

마지막 두 커밋의 차이를 확인했다.

- 91e5233: 답글을 팝업과 휴대폰 알림에서 분류하는 조건·문구 변경.
- dd0cc82: 알림 클릭 후 앱 창에 이동 요청 전달, 응답이 없으면 해당 주소로 이동.

두 변경에는 푸시 등록 API 호출이나 구독 해제 변경이 없다. 해당 변경이
등록을 끊었다는 직접적인 코드 근거는 찾지 못했다.

이전 앱은 ytt.push의 저장된 켜짐 여부만 표시했다. 서버에서 등록이 삭제되거나
브라우저의 주소가 바뀌어도 점검하거나 복구하지 않았다.
마스토돈은 푸시 전송 시 일부 4xx 응답(408·429 제외)을 받으면 등록을 삭제한다.
서버 이메일 설정에 따라 푸시 등록이 없을 때 멘션 메일이 발송될 수도 있다.
이는 가능한 설명이며, 이번 발생 원인으로 확정된 내용은 아니다.

## 추가한 동작

- 앱 시작, 화면 복귀, 인터넷 재연결, 알림 설정 진입 때 실제 등록 점검.
- 앱이 보이는 동안에는 5분마다 점검. 일반 자동 점검은 최소 1분 간격.
- 설정 화면 진입도 일반 점검 간격을 적용해 반복 진입 시 추가 요청을 줄임. 수동 다시 연결하기와 알림 종류 변경은 즉시 반영.
- 자동 점검을 건너뛸 때는 계정 저장소 읽기와 브라우저 잠금도 생략.
- 브라우저 연결 없음·만료, 서버 등록 404, 서버와 브라우저의 주소·공개 키 차이를 확인해 재등록.
- 같은 서버에서 원래 알림을 켜 둔 계정만 복구. 정상 등록에는 불필요한 POST를 하지 않음.
- 서버 등록이 모두 사라졌다면 브라우저에 죽은 주소가 남았을 수 있어 연결도 새로 생성.
- 인터넷·서버·인증 오류를 등록 없음과 구분. 일시 오류만으로 정상 연결을 해제하지 않음.
- 권한 요청은 사용자가 켜기·다시 연결하기를 누를 때만 수행.
- 사용자가 끄기를 누르면 진행 중 복구보다 우선하여 등록을 정리. 같은 브라우저의 작업은 직렬화.
- 서비스 워커의 pushsubscriptionchange 신호를 받으면 열린 앱에 즉시 점검 요청.
- 설정에 현재 연결 상태, 다시 연결하기, 최근 연결 기록 추가.

기록은 이 기기에 최근 20건만 보관하며 계정·시각·점검 결과·HTTP 상태 번호만 저장한다.
인증 토큰, 푸시 주소, 암호화 키, 글 내용은 기록하지 않는다.
서비스 워커에 인증 토큰을 새로 보관하지 않는다.

## 복구 범위

브라우저가 앱과 서비스 워커를 모두 실행하지 않는 동안에는 즉시 복구를 보장할 수 없다.
pushsubscriptionchange도 모든 브라우저에서 지원되지는 않는다.
따라서 앱이 다음에 실행되거나 화면으로 돌아오면 다시 확인한다.
휴대폰 설정에서 알림을 막았거나 재로그인이 필요한 경우에는 안내를 보여 준다.
서버 등록 확인 성공은 실제 알림의 최종 수신을 보장하는 전송 검사가 아니다.

## 검증

추가 의존성 없이 Node.js로 실행한다.

```sh
node --test tests/push-recovery.test.cjs
```

정상 연결, 서버 등록 유실, 브라우저 연결 유실·만료·주소 및 키 변경,
권한·오프라인·401·429·503, 복구 도중 끄기, 켜기 도중 취소,
비활성 계정과 다른 창에서 로그아웃한 계정 제외, 실패 후 재시도,
중복 점검 제한, 브라우저 잠금, 기록의 인증 정보 제외, 서비스 워커 신호를 검사한다.

DOM을 이용한 별도 모의 검사에서 알림 설정의 자동 복구 표시, 연결 기록,
끄기·켜기 버튼 동작도 확인했다. 실제 안드로이드의 백그라운드 중단과
푸시 전송은 모의 환경으로 검증하지 못했다.
